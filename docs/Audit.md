# Hosted incremental execution audit — 2026-10-01

This audit informs Fidelity.FSharp.Incremental, a standalone F# library with its own API and implementation. It will not wrap or depend at runtime on FSharp.Data.Adaptive (FDA) or IcedTasks. Their ideas and experience are valuable inspirations: FDA's maintainers developed a substantial adaptive computation engine; Jimmy Byrd and the IcedTasks contributors developed useful deferred and cancellable task abstractions. Any adapted source must preserve applicable license notices and provenance. Forge hosting is planned; the owner will arrange the GitHub mirror. Composer adoption has not occurred.

The inspected sources are FDA [`76afc00027b10933606e733ff6258275c53224b3`](https://github.com/fsprojects/FSharp.Data.Adaptive/tree/76afc00027b10933606e733ff6258275c53224b3) and IcedTasks [`c51e9fc63fb0c78887f5c418b0530453a2b2cf80`](https://github.com/TheAngryByrd/IcedTasks/tree/c51e9fc63fb0c78887f5c418b0530453a2b2cf80). Conclusions concern these pins and the bounded .NET experiments below, not every release, operator, or workload. The FDA probe assembly SHA256 is `aeaea1b6ed21837d3ee00660164b8ea59a7de4edbd5d14a5e8d3be6bf94b8c69`.

FDA's core incrementality is implemented. Tracked reads register dependencies, invalidation propagates through a level-ordered graph, and demand recomputes dirty values. Dynamic bind detaches obsolete inner dependencies. Collection readers propagate deltas, while histories let readers catch up from different versions. Equality controls cache reuse; weak references limit graph retention but do not replace deterministic subscription or resource disposal. These mechanisms are useful foundations, not a compiler revision certificate or an atomic multi-input snapshot. The remembered documentation passage describing unfinished “Incremental” work remains unidentified. Current source and historical renaming establish an existing engine, without establishing completeness of every feature. [Core evaluation](https://github.com/fsprojects/FSharp.Data.Adaptive/blob/76afc00027b10933606e733ff6258275c53224b3/src/FSharp.Data.Adaptive/Core/AdaptiveObject.fs#L141-L202), [history](https://github.com/fsprojects/FSharp.Data.Adaptive/blob/76afc00027b10933606e733ff6258275c53224b3/src/FSharp.Data.Adaptive/Traceable/History.fs#L374-L469).

Three isolated runtime probes confirmed narrower core problems. Both `AdaptiveToken.Cancelable` and `WithCancellationToken` accepted an already-cancelled token, executed the computation once, and returned 42. Their implementation discards the token. Historical commit `9e59a9e5841ff789e5552652c19c6608e24857ae` explicitly removed cancellation-token storage while retaining those signatures; this does not explain the author's reason for retaining them. Dependency invalidation and cancellation are separate mechanisms. [Token implementation](https://github.com/fsprojects/FSharp.Data.Adaptive/blob/76afc00027b10933606e733ff6258275c53224b3/src/FSharp.Data.Adaptive/Core/AdaptiveToken.fs#L33-L47), [removal](https://github.com/fsprojects/FSharp.Data.Adaptive/commit/9e59a9e5841ff789e5552652c19c6608e24857ae).

A transaction action that changed an input from 1 to 2 and then threw left the cached doubled value at 2, rather than 4. A subsequent valid transaction restored coherence in that sample. Rollback is not promised; the measured concern is the changed input remaining paired with a cache that was never marked dirty. Separately, an exception from public low-level `AddMarkingCallback` left thread-local `Transaction.Running` installed. A later transaction returned normally but produced 11 instead of 21. Ordinary value `AddCallback` uses a different finalizer path, so this result must not be generalized to every callback exception. [Transaction implementation](https://github.com/fsprojects/FSharp.Data.Adaptive/blob/76afc00027b10933606e733ff6258275c53224b3/src/FSharp.Data.Adaptive/Core/Transaction.fs#L164-L267).

Ten selected upstream tests passed: eight collection/history controls and two callback concurrency controls. The latter exercise the current repair for a specific callback lock inversion and safe delayed cleanup. They coexist with the new counterexamples; neither establishes general brokenness or a full-suite pass. [Callback repair](https://github.com/fsprojects/FSharp.Data.Adaptive/pull/121/files).

IcedTasks runtime retries confirmed ordinary cold/cancellable factory reinvocation, inherited tokens, pre-cancelled invocation refusal, and awaited asynchronous disposal. They also characterized cooperative limits: a synchronous loop completed ten iterations after cancellation, and a tokenless hot task resumed with 42. `parallelZip` returned a fault while its sibling remained pending; ordinary `whenAll` joined, but a child cancelling the token during startup let its parent cancel before that child finished. These observations distinguish cancellation checkpoints and child ownership; probe-group “PASS” labels do not mean every behavior meets the proposed host contract. Repeat-invocation counterexamples returned 1 twice, with only one body start, from both `backgroundColdTask` and a separately executed `backgroundCancellableTask` probe under the default scheduler. Ordinary counterparts passed. Initial FSI syntax failures are excluded from runtime evidence. [Builder guidance](https://www.jimmybyrd.me/IcedTasks/Explanations/Choosing-a-builder.html), [cancellation guidance](https://www.jimmybyrd.me/IcedTasks/How-To-Guides/Use-cancellable-task-family-for-request-cancellation.html).

The new library should specify ownership before convenience operators: a work owner may cancel execution; an individual waiter may cancel only its wait. Cold-start and repeated-start behavior, sibling cleanup, transaction exception recovery, coherent reads, occurrence multiplicity, history retention, and disposal must have explicit contracts and adversarial tests. Cancellation must be checked before mutation and at publication acceptance, with exceptions unable to strand ambient state. Cached data needs immutable identity and lawful equality; a changed authority or epoch cannot disappear merely because its display value is equal. These are design requirements, not implemented or integrated claims.

Composer remains authoritative at its existing boundaries. Baker owns semantics and complete proof premises; PSG publication copies settled facts; Alex consumes them passively. Solver discharge and artifact correspondence remain separate gates. A host dependency graph may schedule work and display provisional status, but cannot grant proof reuse or publish a stale executable. Compiler epochs, reservation before edits, fresh disk receipts, the serialized CCS gate, and generation acceptance must survive any later integration. This work concerns .NET hosting, not Clef's language-level lazy semantics.
